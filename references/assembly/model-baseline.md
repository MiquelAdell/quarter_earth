# Assembly model baseline (W1)

This document is the numerical oracle for the assembly simulation boundary
(W5). It records what the reference workshop actually does, which eight
opening cards are used, and the tolerances that apply before any assembly run
is compared. It describes existing behaviour, with two approved changes:

- the native climate fix in §4 (`Climate::add_emissions`), which makes the native path deterministic;
- the production-allocator fix in §7.1 (`engine/src/production/planner.rs`), which stops idle processes from using up an allocation turn.

**The allocator fix diverges from upstream Half-Earth Socialism:** in land-
or resource-scarce years the same inputs produce different results. Fixtures
live in `fixtures/`; see `fixtures/README.md` for how to regenerate them.

### 1.1 The two workshop worlds differ

The brief and `references/simplification/m1-run-sheet.md` refer to
`workshop-m1.world`, which was loaded from the main menu for the July M1
session. The current workshop path does not load that file. It loads the
embedded `WORKSHOP.world`. The two files differ in three ways:

- m1 has no `lifespan` or `planning_anchor` fields. They default to 60 and `None`, so m1 boundaries are `year % 5 == 0` and the game would end in 2082.
- m1 keeps about 70 legacy `UnlocksProject` edges. For example, Degrowth is unlocked by Esperanto and Energy Quotas by Continental Smart Grid.
- m1 lacks the five `TransferMixShare` cards: Solar Push, Wind Push, Nuclear Expansion, Phase Out Coal and Organic Transition.

All eight cards below are unlocked in 2022 in `WORKSHOP.world`. The five
mix-transfer cards do not exist in m1. **Open question:** the proposal names
"the July workshop" as the comparison reference. If July really ran m1, its
numbers cannot be reproduced against this baseline.

## 2. Annual driver trace (reference workshop path)

Under the workshop flag, a game is set up as follows. `GameState::default()`
builds `State::new(World::workshop())`, and `State::initialize` runs
`update_demand`, `step_production`, `update_project_costs` and
`update_climate(1.1)`. `prepare_game` then calls `WORKSHOP.apply`, which
adds `Flag::ParliamentSuspended`. Next come `init_vars` and `update_factors`,
which are display-only. `UIState.start_year` is 2022 and `UIState.emissions`
starts empty. `GameView::new` goes straight to Planning.

Each cycle then runs these steps (`game/src/views/{mod,session/mod,world,report}.rs`):

1. **Planning (`Session::new`).** `WORKSHOP.begin_planning` sets `political_capital = 30`, discarding any unspent PC. The world/event rolls return nothing in workshop mode. `collect_research_points` runs. Passing a card goes through `workshop::toggle_policy` → `pay_points`, which requires `status == Inactive` and PC ≥ cost, then `pass_policy` → `State::start_project`. The card's status becomes `Building` and its ID is pushed onto `policy_queue`, so pass order is preserved.
2. **World phase (`WorldEvents::new`).** `ui.cycle_start_snapshot` runs. A fresh `Climate::new(start_year = 2022)` is created; if `ui.emissions` is non-empty it calls `set_emissions_data(ui.emissions.clone())`. All event and disaster rolls are empty (`StateExt::roll_events` returns `[]` under workshop, and the world has 0 events).
3. **Every year, in this order (`next_phase`):**
   1. Disasters → ComputeTgav. In the browser this waits until `climate.is_ready()`. Then `get_emissions(state)` converts `state.emissions` with `Emissions::for_hector()`: CO2 goes to Pg C/yr as `ffi_emissions`; CH4 and N2O go to Tg/yr. All three are scaled by `min(1, 200 / |Gt CO2-eq|)`. The values are passed to `climate.add_emissions(...)`, and the result is stored back with `ui.emissions = climate.emissions_data()`.
   2. ComputeTgav: `tgav = climate.tgav(world.year + 1)`. Native returns this synchronously. In the browser it is polled once per frame until the promise resolves.
   3. StepYear: `State::step_year(tgav)` does the following:
      - `step_projects`: advances `Building` projects, then `update_project_costs`.
      - `apply_changes`.
      - `update_demand`.
      - `step_production`: feedstocks, the shortage outlook, and `update_extinction_rate`. Extinction uses the **previous** year's `world.temperature`.
      - `step_world(tgav)`:
        - `update_populations`.
        - `update_climate(tgav)`, which sets `temperature = tgav + temperature_modifier` and selects regional climates from `climates.json` keyed by temperature **rounded to 0.1 °C**. It also updates sea level rise.
        - `regions.develop(stop, fast, degrowth)`.
        - `update_outlook(temp_change)`.
      - `world.year += 1`.
      - If the new year is a pre-planning year (`year + 1` is a planning year), `roll_new_policy_outcomes` runs. It drains `policy_queue` in pass order, rolls each card's outcome, sets the status to `Active`, applies the effects and calls `update_demand`.
   4. Updates and Events (empty) → Disasters. When `year > cycle_start_year && is_planning_year()`, `State::finish_cycle()` runs (NPC seats and `last_outlook`). Then `upgrade_projects` and `update_processes` run; in workshop both are no-ops because the plan screen is policies-only. The cycle ends.
4. **Report.** `check_requests()` runs for display, then Next. If `world.year >= death_year`, which is 2052 (`workshop::has_reached_end`), the game goes to Ending. Otherwise it returns to step 1.

**How temperature enters the step.** Climate is computed outside the engine
and injected as a single scalar.

- `tgav` for `year+1` is computed from the emissions history up to and including the current year's pre-step emissions.
- It enters only through `update_climate`, which drives temperature, regional climates, sea level and the outlook change.
- Extinction picks up the new temperature one year later.
- The first step jumps from 1.10 to 1.37 °C (2023), because the world's initial temperature does not match Hector's history-driven output. Outlook drops from 30.0 to 25.9 that year.

**Policy timing.** A card passed in planning year Y is `Building` from Y+1
through Y+3 and becomes `Active` at the step that lands on Y+4, the
pre-planning year. Its effects first act on production in the step from
Y+4 to Y+5. Policies have 0 points, so `years_for_points` is infinite and
`build()` never completes them. Gated cards unlock at the same moment (Y+4),
so they become passable in the next planning year (Y+5). The runs confirm
both: for example, in scenario b Solar Push is passed in 2022, becomes
`Active` in 2026, and Mass Electrification is unlocked in 2026. Note `Effect * 0.0` for gradual
Building policies: `impl Mul<f32> for Effect` passes `UnlocksProject`,
`AddFlag` and `TransferMixShare` through **unscaled**. While a gradual policy
is `Building`, such effects are re-applied every year.

- Remediate (gradual, unlocks SRM) therefore unlocks SRM in the year after it is passed.
- Mass Electrification (gradual, `AddFlag Electrified`) pushes a duplicate flag every year it is Building.

Neither card is in the eight below or in the parity scenarios. W5 must
reproduce this behaviour if it exposes them.

## 3. Cycle years

The engine and game code agree with the spec's six five-year rounds:

- Planning years are **2022, 2027, 2032, 2037, 2042 and 2047**. `World::is_planning_year` uses `planning_anchor` 2022, and the engine test `test_workshop_planning_boundaries_and_pre_boundaries` covers this.
- Pre-planning years are 2026, 2031, 2036, 2041, 2046 and 2051.
- The end year is **2052**: `death_year = 2022 + 30`. The report after the 2047–2052 cycle routes to Ending (`views/mod.rs` test `workshop_final_report_goes_to_ending_not_a_seventh_plan`).
- `workshop_cycle()` labels the rounds 1–6.

The execution-log note "boundaries are `year % 5 == 0` … ending fires at
2055" in `references/simplification/implementation-plan.md` (2026-07-02, W5
gotcha) is **stale**. The anchor and lifespan fields fixed it. It is still
true for `workshop-m1.world`, which lacks those fields. **No spec conflict
exists for the reference world. The conflict exists only if m1 is treated as
the reference** (§1.1). The stale log line should be corrected in the
simplification docs; that is not done here.

## 4. Browser vs native climate path (input to design decision 3; no decision made)

| Aspect | Native (`game/src/climate.rs`, hector-rs FFI) | Browser (`game/assets/js/hector/tgav.js` + `hector.wasm`) |
|---|---|---|
| Call model | Synchronous. A new Hector instance is built per call, and the full history is integrated from 1765 to `year+1` | Async promise, polled each frame. **One persistent Hector instance per `Temperature`**: `prepareToRun` happens once, then each `run(endDate)` continues from the previous end date after re-setting all emissions arrays |
| Instance lifetime | Stateless | A new `Temperature` per world phase (per cycle), so each cycle's first call integrates from 1765 |
| Readiness | Always ready | `isReady()` is false until `config.json`, `rcp26.default_emissions.json` and `rcp26.to_2050.json` are fetched. `setEmissions` before readiness is buffered. The world phase blocks at Disasters → ComputeTgav until ready |
| History data | Compiled into hector-rs (`get_emissions(2022)`) | `rcp26.to_2050.json` sliced to 2022 |
| `ui.emissions` shape | Nested `{section: {source: [..]}}` | Flat `{source: [..]}`. **Saves are not portable between native and web** |
| Appended year | `add_emissions` appends each key to **every** section that contains it, so NOX, CO and NMVOC go to both `OH` and `ozone`. This matches the browser. See the history note below | Every section that lists the source gets the same flat series, so both `OH` and `ozone` receive the default |
| `endDate` | `year+1`, with series padded by their last value | `1765 + len` (= `year+1`); Hector handles the missing final point itself |
| Determinism | Bit-identical across processes for a given build profile. Debug and release builds differ by at most 1 f32 ulp (§8) | Node replays of `hector.wasm` were bit-identical run to run |

**History of the native fix.** Before the fix, the native path wrote each
key only into the **first** section that contained it. The loser section
(`OH` or `ozone`) was padded by `run_hector` with its 2021 value (NOX 36.1
instead of the default 29.0). The winner depended on `HashMap` iteration
order, so every process, and every reload, picked one of two trajectories at
random. Those trajectories differed by up to 0.028 °C and 1.3 outlook by 2052.

Since the fix there is a single native trajectory. It lies within 0.002 °C
of the former `ozone_appended` variant. The unit tests in `climate.rs` pin the
fix: both sections are appended, and every series has the same length.

Measured effect (open loop). The native fixtures' Hector inputs were fed to
the real `hector.wasm` via `references/assembly/tools/assembly_web_replay.mjs`,
mirroring the `tgav.js` bookkeeping. Browser tgav minus native tgav:

| Scenario | Min | Max | Note |
|---|---|---|---|
| a | −0.0022 °C | 0.0000 °C | |
| b | −0.0020 °C | +0.0064 °C (2052) | Grows with step changes in emissions (§7.1) |
| c | −0.0016 °C | +0.0009 °C | |
| d | −0.0022 °C | +0.0087 °C (2042) | Grows with step changes in emissions (§7.1) |

Both paths now feed the same values into each Hector section, so the
remaining gap comes from four other differences:

- the native path re-integrates from 1765 every year, while the browser instance continues from its previous run;
- final-year handling: the native path pads with the last value, while the browser path uses `endDate` and lets Hector handle the missing point;
- the source of the history data;
- the wasm and native compilers.

The gap is small and smooth under steady emissions, but large when emissions
alternate year to year. Emissions, production and demand did not depend on
temperature in any scenario: they were identical across the two former
variants. The open-loop replay is therefore effectively closed-loop for
temperature and sea level. A browser session has **not** been captured, so
outlook, habitability, extinction and region development remain unverified
on that path. These are the fields driven by the 0.1 °C climate-table
rounding.

Implications for snapshots vs deterministic reconstruction:

- **Round-boundary snapshot** of `hes_engine::State` + `ui.emissions`:
  - Browser: equivalent to uninterrupted play, because normal play already recreates the climate model at every cycle start from the stored emissions.
  - Native: also equivalent. Since the fix, results no longer depend on `HashMap` order, so a reload (a newly deserialised map with a new hasher) gives the same trajectory as uninterrupted play. **The earlier reload-flip issue is gone.**
- **Deterministic reconstruction** from 2022 plus the ballot list: reproducible on both paths, and on native across processes. Cost is one Hector integration per simulated year. The native debug build took about 15 s of CPU per 30-year scenario; browser timing was not measured.
- Mid-cycle snapshots on the browser path would differ slightly from uninterrupted play, because they break the incremental integration. Snapshot only at round boundaries.
- RNG: see §7. The eight cards are RNG-free.

### 5.1 Gates and exclusions in the whole 21-card deck

`UnlocksProject` gates are the only prerequisites, and the 18 other cards
are unlocked from the start. A gate fires when the prerequisite becomes
`Active` in the pre-planning year.

| Gated card (cost) | ID | Unlocked by (OR) |
|---|---|---|
| Cellular Meat (10) | `f641150a-2501-459a-ada9-d0ffeb252c01` | Regenerative Agriculture (`b3a75f9b-7d54-4df7-96b8-9c84e9ad2749`) |
| Mass Electrification (15) | `cf745bf7-96ba-4fde-8f92-ab6b7e1b3c33` | Solar Push, Wind Push (`bd4c9fc9-e02d-573a-9c65-2d0fe2d9bc56`), Nuclear Expansion (`7afdb82b-b822-5965-a77a-23b8739a7bcd`) |
| Solar Radiation Management (SRM) (10) | `4d39c88b-08e1-4f96-a0ea-acc9b244c279` | Remediate and Protect Ecosystems (`7a11d379-19aa-4eb7-932d-0dd9bca568d4`). It is gradual, so the unlock happens the year after it is passed (§2) |

Exclusions:

- `project_lockers` is empty and the deck has no `LocksProject` effects, so there are **no declared mutual exclusions**.
- There is one **hidden exclusion**. `TransferMixShare` is a silent no-op when the source share is below the amount, and coal electricity starts at 7 units. Solar Push takes 4, Nuclear Expansion 3, and Phase Out Coal 5.
  - **Phase Out Coal + Solar Push** cannot both act: 4 + 5 > 7.
  - **Phase Out Coal + Nuclear Expansion** cannot both act either: 3 + 5 > 7.
  - In each pair, whichever is applied second (by queue order or by cycle) still costs PC, shows as `Active`, and does nothing.
  - Solar + Nuclear together are fine (7). The repeal path (`unapply`) is guarded the same way.
- Other cards fail by the same mechanism only if a source drops below the amount: Wind Push takes 4 from Gas Power, which starts at 5; Organic Transition takes 4 from Industrial Crop Ag, which starts at 14, so it cannot fail in this deck.
- The parity scenarios avoid the hidden exclusion. It is a natural candidate for the invalid-amendment scenario.
- Other invalid amendments the engine itself rejects:
  - passing a locked card;
  - passing a card that is not `Inactive`;
  - exceeding the remaining PC.
- Same-cycle repeal refunds the cost; repealing a card passed in an earlier cycle refunds nothing (`toggle_policy`).

### 7.1 Land squeeze: mechanism and the allocator fix

**Verdict before the fix:** the land shortage was real, but the 0% and the
year-to-year on/off pattern came from the production allocator. They were
not caused by a NaN, a division by zero or clamping. Upstream and the
reference game at `cb487502` behave the same way, because both run the same
`State::update_demand` path; workshop mode does not override it. The trace
came from an instrumented **copy** of the engine.

1. **Land available to production is fixed by protection.** At `engine/src/state.rs:316-317`, `resources.available.land = starting land × (1 − protected_land)`. Preserves take protection to 40%, leaving 60%. Land demand from processes and industry grows with population and income: 53% in 2026 → 68% in 2041 → 78% in 2052. The reported land use is that demand plus the protected 40%. Production can never consume more than the 60%.
2. **Allocation is greedy, first come first served** (`engine/src/production/planner.rs:226-259`). In each pass, every output (fuel, electricity, plant calories, animal calories, in that order) pops its best-ranked remaining order. That order produces `min(order, feedstock_max, resource_max)` (`planner.rs:138-148`) and deducts what it uses from the shared land pool (`planner.rs:150-152`). There is no proportional rationing. **This still holds after the fix.**
3. **Unused processes wasted turns — fixed.** `Processes::orders` (`engine/src/production/processes.rs:217-218`) creates an order for every process, including locked ones and ones with a 0 share. Before the fix, these 0-amount orders were ranked and popped like real ones. In the 2041 step, electricity spent its first two picks on Nuclear Fusion and Retired Coal Capacity while livestock and crop farming took all the land. Every real power plant, even land-light Nuclear and Gas, produced 0.
   - **Fix (`planner.rs:235-249`):** after popping, the planner keeps popping past orders whose amount is ≤ 0. Their `produced` entry stays 0, so a 0-amount order no longer uses up its output's turn. Ranking, scoring and production for orders with an amount are unchanged.
   - Engine tests `test_zero_amount_order_does_not_use_up_a_turn_when_land_is_scarce` and `…_is_identical_when_land_is_plentiful` pin both cases. The scarce test produced `[0, 0, 50]` before the fix and `[0, 10, 40]` after.
4. **Energy inputs to production lag by one year — not changed** (`state.rs:343-344`). Next year's `resources.available.{electricity,fuel}` are set to this year's output. Farming needs electricity and fuel (`planner.rs:142-146`). Before the allocator fix, a 0% electricity year made the next year's farm orders `0 / v = 0` (0% food), which freed the land so power was 100%, and so on: a period-2 oscillation. After the fix, electricity no longer reaches 0, so the oscillation is gone. The lag still causes the isolated one-year dip in d 2048. Changing the lag is a separate decision.
5. `shortages_outlook` uses a penalty of 60 (`state.rs:16`), so values above 30 are valid. `game_over` stays false, because `check_game_over` only runs inside effects; the workshop ignores it anyway.

**Effect on the other scenarios (fixtures at `cb487502` vs now).**

- a and c: discrete state identical; numeric changes are at the f32 last-bit level (≤ 2.8e-7 relative; for example emissions 7.6e-6 Gt and outlook 3.8e-6). Land never binds in a or c, but skipping idle orders changes the pick order. That changes the order in which byproducts are summed and resources are subtracted.
- b and d change materially in their land-scarce years, as tabled above.

For the room, any package that pushes land demand past `1 − protected_land`
still produces a real, now gradual shortage. Without preserves, demand stays
under the pool through 2052: scenario a ends at 78% demand against a 90% pool.

## 8. Variability and tolerances

**Sources checked.**

- **RNG.** `fastrand` is seeded from entropy per process and is used only in `roll_project_outcome` and the event pool. All 20 deck cards except SRM have one `Guaranteed` outcome, so `roll_project_outcome` consumes a random number but cannot change the result. SRM has a `Likely` first outcome (+4 extinction) and a `Guaranteed` fallback, so it is **the one RNG-dependent card**: W5 must seed or fix that outcome if SRM is offered. Events are disabled in workshop mode, and `world.events` is empty.
- **HashMap order (fixed).** Before the §4 fix this was the only observed source of variation, with two native trajectories per scenario. It is gone.
- **Reproducibility (climate and allocator fixes).** For each scenario, 3 debug-build and 3 release-build processes ran (`fixtures/reproducibility.json`). Every process within a profile was bit-identical, and `OH` and `ozone` NOX lengths were equal in every run. Debug vs release: bit-identical in a and d. In b and c, `extinction_rate` differed by one f32 ulp (7.6e-6) from 2040, with no other differences.
- **Browser (open loop, §4).** Temperature differs from native by at most 0.0022 °C in a and c, and by up to 0.0087 °C in b and d, where emissions change in steps. Closed-loop browser outlook, extinction and habitability are unmeasured.
- **Non-linearity.** Regional climates switch at 0.1 °C steps, so even a 0.02 °C temperature difference can produce a step change in habitability and outlook. Outlook tolerance cannot be derived from temperature tolerance. Before the fix, a 0.028 °C spread produced up to 1.3 outlook difference and up to 2.8 regional habitability difference.

**Tolerances, fixed before any assembly comparison:**

- *Native*: W5 runs the native path and compares against `fixtures/<scenario>.json`. Results are bit-identical in practice. The small tolerances only absorb last-bit f32 differences between build profiles or compilers.
- *Browser (provisional)*: closed-loop browser values are **unverified**. The bounds are derived from the open-loop maximum (0.0087 °C now; 0.0173 °C before the allocator fix) plus margin, and from the pre-fix climate-to-outlook sensitivity (0.028 °C produced 1.3 outlook). Validate them with one recorded browser run per scenario before relying on them.

| Field | Native | Browser (provisional) |
|---|---|---|
| Discrete state (year, flags, `policy_queue` order, card status/locked/outcome, mix shares, region income, game_over) | exact | exact |
| `political_capital` | exact only if W5 routes passes through `pay_points`/`state.political_capital`; otherwise not compared. Instead check the ballot: the sum of passed card costs must be ≤ 30 per round | same |

## 9. Open questions and risks

1. **Which world is "the July reference"** (§1.1)? If it is m1, this baseline is not comparable.
2. **Resolved:** native climate nondeterminism. Miquel decided to fix it: `Climate::add_emissions` now appends to every matching section, so there is one native trajectory and no flip after reload (§4, §8).
3. **The browser trajectory differs slightly** (up to 0.009 °C open loop, §4). Closed-loop parity has not been measured; it needs one recorded browser run per scenario.
4. **Hidden exclusion**: Phase Out Coal vs Solar Push or Nuclear Expansion (§5.1). The assembly must reject or warn, or the room pays for a no-op.
5. **Gradual-policy quirk** (§2): SRM unlocks early and Electrified duplicates. Relevant if the second set of eight includes Remediate or Mass Electrification.
6. **SRM is RNG-dependent** (§8).
7. **Land squeeze** (§7, §7.1): Expand Nature Preserves alone (d), or with Luxury for All (b), pushes land demand past the unprotected pool.
   - After the allocator fix the shortage is gradual: food falls to 73% in d and 36% in b, while electricity and fuel lose supply in coarse steps.
   - Outlook goes negative: −14 in d by 2052.
   - The one-year energy lag (`state.rs:343-344`) still causes isolated dips and is an open decision.
   - This is a balance and political-reading risk; review it before the pilot. The spec says to change menu or rules via amendment, not coefficients.
8. **First-year temperature jump** of 1.10 → 1.37 °C (§2) will show as a large round-1 change on the Planet view.
9. The execution log's "2055" note is stale (§3); the simplification docs need a correction.
10. **Harness equivalence.** The harness (`game/examples/assembly_baseline.rs`) compiles `climate.rs` and `consts.rs` verbatim. It mirrors `get_emissions`, `pay_points`/`pass_policy`, `begin_planning`, `WORKSHOP.apply` and the `WorldEvents` ordering line for line. It cannot instantiate `WorldEvents`/`GameView` itself, because they need an egui/GL context (`GlobeView`) and private game modules. Divergence risk: any later change to those game functions must be mirrored in the harness.
11. **Upstream divergence.** The allocator fix (§7.1) means this engine no longer matches upstream Half-Earth Socialism when land or other resources are scarce. Do not compare such years against upstream builds or the original web game.
